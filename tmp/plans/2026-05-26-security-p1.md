### Группа A — low-risk полировка (без миграций)

**Файлы:** `services/auth.py`, `routers/auth.py`, `deps.py`.

- п. 7 — Email collision UX (НЕ маскируем enumeration, по решению Никиты Олеговича 2026-05-26):
  - В `routers/auth.py:register_submit`: при `AuthError("email_taken")` оставить status_code=400 + render `auth/register.html` с сообщением «Email уже занят. [Войти →]» — ссылка ведёт на `/auth/login?email=<prefilled>`.
  - В `templates/auth/register.html` — обновить блок ошибки: если `error_code == "email_taken"`, рендерить ссылку отдельно от текста.
  - В `templates/auth/login.html` — при наличии query-param `email` — префилл поля.
  - **Trade-off:** email enumeration остаётся возможным через register-endpoint. Защита через login (п. 8 — выравнивание тайминга) сохраняется.
- п. 8 — Timing-выравнивание:
  - В `services/auth.py`: завести модуль-константу `_DUMMY_ARGON2_HASH = hash_password("dummy_password_for_timing_protection_1234")`.
  - В `authenticate`: при `user is None` выполнить `verify_password(password, _DUMMY_ARGON2_HASH)` перед возвратом.
- п. 10 — Различать HTML vs JSON в `require_user`:
  - В `deps.py:require_user`: проверять `request.headers.get("accept", "")`. Если `text/html` в Accept → 303 redirect. Иначе → 401 JSON `{"detail": "not_authenticated"}`.
  - Потребует доступ к `Request` — добавить `request: Request` в сигнатуру.

**Verification:** restart site, `curl -X POST /auth/register` с уже занятым email → шаблон `verify_sent.html`; `curl -H "Accept: application/json" /cabinet` → 401 JSON; ручная регистрация в браузере не сломалась.

**Commit:** `security: harden auth flow (timing, email enumeration, HTML/JSON branching)`

### Группа B — хэширование session_id (миграция)

**Файлы:** `models/session.py`, новая Alembic-миграция, `services/sessions.py`, `main.py` (middleware, обновится в C).

- Миграция `0002_session_hash_id.py`:
  - Добавить столбец `session_hash` (String(64), unique, indexed, nullable=False, server_default = `''` для совместимости).
  - Backfill для существующих сессий пропустить — они expire'нутся за TTL=720h, либо принудительно `UPDATE sessions SET expires_at = NOW() WHERE expires_at > NOW();` после deploy.
  - В downgrade — drop колонки.

- `models/session.py`:
  - Текущий `id` остаётся primary key (для совместимости со старыми ссылками в коде), но переименовать смысл: `id` → теперь произвольный, реальный поиск по `session_hash`.
  - Альтернатива: оставить `id` как обычный auto-id PK, ввести `session_hash` уникальный indexed.
  - Решение: упрощённо — `id` остаётся string-сидом, но в БД пишется хэш plaintext'а. Cookie содержит plaintext, БД — `hash_token_for_storage(sid)`.
  - Принятый вариант: НЕ менять схему, использовать `id` как хранилище хэша. Cookie = plaintext, `Session.id` = хэш. Проще, меньше миграционных рисков.
  - Откат от миграции: вместо новой колонки — просто меняем поведение. Старые сессии сразу перестанут валидироваться. Принудительный logout всех — приемлемая цена при таком security-fix.

- **Финальный план Группы B:**
  - Миграция НЕ нужна.
  - `services/sessions.py:create` — `Session(id=hash_token_for_storage(sid), ...)`, в cookie — plaintext `sid`.
  - `services/sessions.py:get` — `select(Session).where(Session.id == hash_token_for_storage(sid))`.
  - `services/sessions.py:revoke` — то же.
  - Redis-ключ — оставить `sess:{plaintext_sid}` (Redis не утечёт через SQL-инъекцию).
  - После deploy: все 5 текущих пользователей разлогинятся, повторно войдут. Это OK.

**Verification:** restart site, логин в браузере, проверка cookie в devtools (plaintext base64), `psql -c "SELECT id FROM sessions LIMIT 1;"` → hex-хэш SHA-256 (64 chars).

**Commit:** `security: store sha256 hash of session id in db (plaintext only in cookie)`

### Группа C — middleware unification + CSRF

**Файлы:** `main.py`, `deps.py`, `routers/{auth,admin,cabinet}.py`, `templates/base.html` + все формы.

- п. 5 — Унификация:
  - `main.py:attach_current_user` middleware: вместо прямого `select(Session)` — `SessionService(db, redis).get(sid)`.
  - Заодно использовать `async_session_factory()` через context manager (как уже сделано).

- п. 1 — CSRF:
  - В `deps.py` добавить `verify_csrf_token(request: Request, session_id: Cookie(alias="session"))`:
    - читать `session_id` из cookie;
    - читать submitted token из form-data (`request.form()`) либо header `X-CSRF-Token`;
    - вызывать `verify_csrf(session_id, submitted)`; на mismatch — 403.
  - В layout (`templates/base.html`) добавить `<meta name="csrf-token" content="{{ csrf_token }}">`.
  - В каждый template с `<form method="POST">`: `<input type="hidden" name="csrf_token" value="{{ csrf_token }}">`.
  - В каждый POST-роут в `routers/{auth,admin,cabinet}.py` добавить `Depends(verify_csrf_token)`.
  - Контекст-процессор: middleware устанавливает `request.state.csrf_token = generate_csrf(sid)` если sid есть.
  - Шаблоны рендерятся с `csrf_token=request.state.csrf_token`. Обновить все `TEMPLATES.TemplateResponse(...)` вызовы — добавить в context.

  **Edge case:** `/auth/login` POST вызывается без существующей сессии. Решение: для login/register/verify CSRF не обязателен (нет сессии для double-submit). После создания сессии CSRF обязателен для всех state-changing операций.

**Verification:** ручной POST `curl -X POST /cabinet/keys/1/revoke -b "session=..."` без csrf_token → 403; через браузер с формой — работает.

**Commit:** `security: enforce csrf on cabinet/admin posts + unify session middleware`

### Группа D — rate-limit + brute-force counter

**Файлы:** `services/auth.py`, `routers/auth.py`, новый `app/security/rate_limit.py`.

- п. 3 — Активация колонок:
  - В `services/auth.py:authenticate`:
    - Чек `user.locked_until > now()` → `"locked"`.
    - На fail — `failed_login_count += 1`; при >= 10 → `locked_until = now() + 30min`.
    - На success — reset.
  - В `routers/auth.py:login_submit`: mapping `"locked": "Аккаунт временно заблокирован, попробуйте через 30 минут"`.

- п. 2 — Rate-limit (Redis-counter):
  - Новый модуль `app/security/rate_limit.py` с функцией `check_rate(redis, key, limit, window_seconds)`:
    - `INCR key`; если =1 → `EXPIRE key window`; если > limit → raise `RateLimitExceeded`.
  - В `routers/auth.py`:
    - `login_submit`: `await check_rate(redis, f"rl:login:{ip}:{email_normalized}", 5, 900)`.
    - `register_submit`: `await check_rate(redis, f"rl:register:{ip}", 3, 3600)`.
    - `verify_email`: `await check_rate(redis, f"rl:verify:{ip}", 10, 3600)`.
  - На `RateLimitExceeded` — отдавать 429 с user-friendly сообщением.

**Verification:** `for i in {1..10}; do curl -X POST /auth/login -d 'email=test@test.com&password=wrong'; done` → 6-я попытка 429; DB `SELECT failed_login_count, locked_until FROM users WHERE id=1;` после 10 fails → counter=10, locked_until заполнен.

**Commit:** `security: rate-limit auth endpoints + activate brute-force lockout`
